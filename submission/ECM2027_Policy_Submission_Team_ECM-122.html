1. What the policy does

Multi-demonstration trajectory following for the Galbot-Mobile dual-arm chamber task in the official simulation (scene04_1.usd).

  • At reset, the policy picks the recorded demonstration whose first-frame

end-effector positions are nearest to the robot's observed initial positions. Selection happens only at reset, so a rollout never jumps between demonstrations mid-episode. Without an observation at reset the first demonstration is used.

  • During the episode it tracks a phase index into the chosen demonstration

and advances it monotonically. When the caller supplies the robot's current end-effector positions it re-anchors the phase to the demonstration point nearest the current pose within a forward window (closed-loop phase tracking); otherwise it advances one demonstration step per policy step. The re-anchoring may move the phase at most 4 demo steps per policy step (advance cap, §3): a noisy observation can otherwise yank the phase hundreds of steps forward in one step.

  • It commands the demonstration pose at phase + lookahead for both

arms, as absolute differential-IK pose commands (use_relative_mode=False, the starter repository's own convention).

  • On Batch 2 and Batch 3 demonstrations it replays the recorded gripper state:

gripper_pos is the Galbot gripper joint position (0.0 fully open, 1.703 fully closed), thresholded at the range midpoint 0.8515 into the binary gripper action (< 0 close, >= 0 open), the starter repository's own BinaryJointPositionAction convention. Batch 1 demonstrations carry no gripper channel, so on those the grippers are held at a fixed configurable command. Wheel velocity is commanded zero — see the honest limitation in §5.

The bundled set holds nine real episodes: four Batch 1 (demo_0, demo_2, demo_7, demo_9), two Batch 2 (demo_b2_0, demo_b2_3), and three Batch 3 (demo_b3_0, demo_b3_1, demo_b3_2), extracted from nine independent recordings of the official dataset rocochallenge2025/ecm2027_sim_data. Episode lengths: 7,471 / 5,632 / 7,566 / 5,122 / 4,106 / 4,022 / 4,503 / 5,823 / 6,163 steps. Batch 2 files carry the split observation terms obs/eef_pos + obs/eef_quat (composed into the same (T, 2, 7) shape by the loader) plus a real gripper observation obs/gripper_pos (T, 2), stored in the demo_b2_* bundles. Batch 3 ships as one .tar.gz per recording (each holding a single galbot_success.hdf5); it uses the same split layout plus a real gripper observation, stored in the demo_b3_0, demo_b3_1 and demo_b3_2 bundles. Batch 3 was released 2026-11-17, eleven days before the announced 2026-11-28 date; all three Batch 3 tarballs are now downloaded, extracted, and integrated. (The Batch 3 listing on the dataset page has since grown to 200 recordings, last checked 2026-11-19; this package integrates the third recording in sequence.) One honest caveat: Batch 3's first frame is bit-identical to Batch 2's rest pose (first-frame L2 difference 0.0 against demo_b2_0, demo_b2_3, demo_b3_0 and demo_b3_1), so nearest-start selection ties across the five and resolves to the earliest demo per the documented tie rule; a Batch 3 demo is selected only when the evaluation scene's start pose is nearer to it than to the Batch 2 rest pose.

2. Interfaces

Two adapters share the same core (ecm_policy/core.py, pure NumPy; multi-demo selection in ecm_policy/multidemo.py):

1. Docker policy service (ecm_policy/service.py) — the planned official submission shape, implementing the starter README's service operations health(), reset(task_info), predict(observation), close(). Defaults to multi-demo mode over data/; --trajectory <single .npz> selects the old single-demo mode. 2. In-process adapter (ecm_policy/adapter.py) — builds a MultiDemoCore when trajectory_dir / demo_dir / ECM_TRAJECTORY_DIR is set or when trajectory_path points at a directory, for use with the starter repository's own evaluation harness. 3. Official gRPC policy client (ecm_policy/grpc_client.py, new 2026-11-21) — speaks the participant interface the upstream starter repo published 2026-11-20 (policy_v1.proto, README "Participant policy interface"): the policy is a gRPC client connecting to the evaluator's server at ECM27_EVAL_ENDPOINT, exchanging GetObservation / Step calls with the preferred 19-dimensional actions (arm target poses in (x, y, z, w) order, gripper negative-closes, zero base velocity). The 20-dimensional legacy core output is converted by dropping the wheel commands and appending a zero base velocity; quaternions are emitted in (x, y, z, w) order. The generated policy_v1_pb2.py is vendored from the upstream repo. A Dockerfile.grpc builds the policy image the interface asks for; the build is NOT verified on this host (no Docker here). The organizers published the Docker submission route by mail on 2026-11-20: the policy image is submitted through the official form (see §6).

A Dockerfile is included in the repository. The starter README now publishes the official Docker service transport and message schemas (2026-11-20); the service follows the operation names the starter README publishes, and the gRPC client follows the published protocol.

3. Verification (all CPU-side; this host has no GPU)

  • 113 / 113 tests pass in the repository test suite, measured 2026-11-23

in an isolated clone at the submitted commit (100 pass under the system Python; the 13 skipped tests need h5py — 5 Batch 2 layout tests and 8 scoring-analysis tests — and pass under the data-sample venv Python, where the full suite runs 104/104 with the 9 gRPC tests skipped — that venv has h5py but no protobuf, and PyPI is unreachable from this host to install it; no single interpreter on this host runs all 113), including: full-episode rollout integrity (finite 20-dim actions, unit-norm quaternions, replayed gripper state on Batch 2 and Batch 3 demos and fixed gripper on Batch 1 demos, zero wheels throughout, monotonic phase to trajectory end, no mid-episode demo switch), multi-demo selection, adapter, service, core, and gripper-threshold tests.

  • Official gRPC client tests (tests/test_grpc_client.py, 9 tests):

a fake in-process evaluator replays real demo bundles as protocol observations through real protobuf serialization. A full 4,106-step episode of demo_b2_0 completes with 0 action violations and 99.61% gripper agreement against the recording; a two-environment run (one env per demo) stays independent with per-env reset on termination; FAILED_PRECONDITION on Step recovers via re-GetObservation; transient UNAVAILABLE on GetObservation retries; the run is deterministic across repeats. The socket layer itself (grpcio) is NOT tested here: grpcio is not installable on this host (PyPI unreachable behind the proxy), so the tests drive a fake channel and the real grpc.insecure_channel path is untested. The frame assumption is documented in the module: recorded EE poses are passed through as-is with zero base velocity, and whether they coincide with the evaluator's robot-root frame depends on the spawn pose (upstream issue #5, still open).

  • Offline lagged-follower evaluation (ecm_policy/evaluate.py, full

table in evaluation/results.md): a simulated robot that moves a fraction alpha of the way toward each commanded pose per step. At alpha = 1.0 the policy reproduces every bundled recording exactly (zero position error, zero phase lag); max phase lag strictly decreases as the follower gets faster on all 9 demos; gripper agreement on Batch 2 and Batch 3 rises with alpha (32–42% at alpha = 0.1 to 99.8–99.9% at alpha = 1.0). At alpha 0.1–0.5 the lagging follower cannot keep wall-clock pace (mean position error 0.50–0.70 m) — reported as a baseline, not a score.

  • Lookahead sweep (tools/sweep_lookahead.py, full table in

evaluation/lookahead_sweep.md): every bundled demo at alpha 0.3 / 0.5 for lookaheads 0 / 1 / 2 / 4 / 8. Lookahead 2 is the submission default: it beats lookahead 1 at both swept alphas on demo-averaged mean position error (0.609 vs 0.618 m at alpha = 0.3; 0.010 vs 0.618 m at alpha = 0.5), while lookahead 4 wins only at 0.3 and lookahead 0 stalls the phase tracker outright (final phase 0). The near-perfect alpha = 0.5 / lookahead-2 result is a property of the harness's first-order lag model, not a measurement of real Isaac Sim dynamics, and is reported as such.

  • Observation-noise sweep (tools/sweep_noise.py, full table in

evaluation/noise_sweep.md): every bundled demo at alpha 0.3 / 0.5 with lookahead 2, for Gaussian noise on the EE positions the policy observes (sigma 0 / 1 mm / 5 mm / 1 cm / 2 cm). The phase tracker is noise-fragile: at alpha = 0.5, 1 mm of noise breaks the near-perfect noiseless tracking (mean position error 0.010 -> 0.261 m), and at 5 mm and above the tracker systematically outruns the recording (mean phase lag -918 steps at 5 mm, -1,948 at 2 cm) while gripper agreement on Batch 2 falls to 31.9%. The mechanism is the nearest-point phase search inside its 250-step forward window combined with monotonic phase: a noisy observation can make a later demo pose the nearest one, jumping phase forward, and the jump compounds. At alpha = 0.3 the same jumps partially compensate lag at 5 mm (mean phase lag 1,117 -> 32 steps) but overshoot at 2 cm. Noise was added only to the observation, never to the true robot state or the recorded trajectory. The real evaluator's observation noise is unknown, so this bounds the sensitivity; noise-robust phase tracking is the next step, not a claim made here.

  • Noise-robust phase-tracking sweep (tools/sweep_robust.py, full table

in evaluation/robust_sweep.md): six tracker configs (uncapped baseline, advance caps 4 / 8 / 16, window 32, window 64 + cap 8) at alpha 0.3 / 0.5 with lookahead 2, for Gaussian observation noise (sigma 0 / 1 mm / 5 mm / 1 cm). The baseline column reproduces the M9 numbers exactly. Advance cap 4 is the new submission default: it wins 6 of 8 (alpha, sigma) cells on demo-averaged mean position error, it costs nothing with no noise (identical numbers at sigma 0), and it lifts Batch 2 gripper agreement at alpha = 0.5 at every noise level (sigma 1 mm: 84.3% -> 93.4%; 5 mm: 55.2% -> 76.0%; 1 cm: 43.6% -> 60.0%). The one exception is alpha = 0.3 / sigma 5 mm, where the uncapped tracker wins (0.391 vs 0.593 m) because noisy forward jumps partly compensate the lag — a property of the harness's first-order lag model, not a real-evaluator result, and reported as such. Smaller windows alone help less than the cap, and cap 8 / cap 16 sit between cap 4 and the baseline at most noise levels.

  • Batch 3 re-run of the same sweep (tools/sweep_robust.py, full table

in evaluation/robust_sweep_b3.md, 2026-11-17): the six configs above re-swept over all 7 bundled demos (336 rollouts). Every one of the 288 per-demo rows for the original six demos reproduces the M10 numbers exactly (max difference 0.0); only the 7-demo averages move, because demo_b3_0 joins them. Advance cap 4 still holds as the submission default: it wins 5 of 8 cells on 7-demo-averaged mean position error, costs nothing with no noise, and lifts gripper agreement at alpha = 0.5 at every noise level (1 mm: 88.7% -> 94.9%; 5 mm: 57.6% -> 72.8%; 1 cm: 48.4% -> 60.4%). The three cells it does not win: alpha = 0.3 / sigma 5 mm, where the uncapped baseline wins (0.418 vs 0.589 m, the same lag-compensation mechanism as above); alpha = 0.3 / sigma 1 mm, where cap 16 wins by 0.0009 m (a tie in practice); and alpha = 0.5 / sigma 0, where baseline and cap 4 are numerically identical (0.0101 m). demo_b3_0 alone behaves like the other demos: noiseless alpha = 0.5 mean position error 0.0108 m with 99.9% gripper agreement; at alpha = 0.3 it lags like the rest (mean position error 0.666 m, mean phase lag 888 steps).

  • Gripper-threshold sensitivity sweep (tools/sweep_gripper_threshold.py, full table

in evaluation/gripper_threshold_sweep.md, 2026-11-21): five policy replay thresholds (0.2 / 0.425 / 0.8515 / 1.28 / 1.5) at alpha 0.3 / 0.5 with lookahead 2 and advance cap 4, for Gaussian observation noise (sigma 0 / 1 mm / 5 mm / 1 cm), over all 9 bundled demos (360 rollouts). The evaluator's ground-truth recorded-closed labels always use the joint-range midpoint 0.8515; only the policy's threshold varies. The midpoint column reproduces the M14 cap-4 numbers exactly (max difference 2.1e-14). Thresholds 0.2 and 0.425 match the midpoint within ~1 percentage point of gripper agreement in every cell, while 1.28 and 1.5 collapse it by 20–45 points (e.g. noiseless alpha = 0.5: 99.2% at the midpoint vs 58.3% at 1.28 and 51.8% at 1.5) — the recorded gripper signal is strongly bimodal, so any threshold in the low half of the joint range lands in the sparse transition band and performs the same, and only a transition point above ~1.1 would cost agreement. The midpoint stays the submission default: it is the documented convention and the best noiseless performer. Position error is exactly identical across thresholds in every cell, as expected (the gripper action does not feed the pose tracker).

  • Issue-#8 scoring analysis (tools/analyze_scoring.py, full table in

evaluation/scoring_analysis.md, 2026-11-23): the 13-point scoring spec is read from the starter repo's task code, and the demo data's initial_state root poses are measured against the code's randomization claims. Only the sponge pose is randomized in the data (position jitter within the code's +/-0.05 m band in x/y, yaw spread 2.80 rad; recorded z 0.76-0.81 m straddles the spawn band's low edge, i.e. the pose is post-settle on the table). The robot base pose is bit-identical in every sampled initial state although the task code samples +/-0.10 m / +/-0.50 rad per reset, so the policy's zero-base-velocity assumption matches the demo distribution, not necessarily the eval distribution (upstream issue #5). Chamber, both parts, table and lid joints are bit-identical: nothing else is randomized. There is no scored lid-lock point: the lid is scored as lift (1a), stable-open (1b) and stable-closed (6) only, and the word "lock" appears in the task file only in the episode description string. Each wipe face is worth 1 point after 0.5 s of continuous sponge-chamber contact while that face is the nearest cavity face to the sponge centre (within 0.08 m, inside the cavity). Per-step demo recordings carry no lid angle, object pose or contact flag, so the wipe and lid scoring rules cannot be reconstructed from demo data; the answers rest on the task code and the organizer mail.

5. Honest limitations

  • **Gripper replay is built and tested; the mapping convention is

unverified by the organizers.** Batch 1 recordings carry no gripper channel, verified across all four independent Batch 1 recordings (each file contains exactly one data/demo_*/ee_poses dataset and nothing else), so Batch 1 cores still hold the fixed command. Batch 2 recordings carry data/demo_*/obs/gripper_pos (T, 2), a real varying signal (0 to 1.703 in the two verified episodes), now consumed by the policy: full-episode open-loop rollouts replay the recorded gripper state exactly (demo_b2_0: 8 open/close transitions, 58.1% closed; demo_b2_3: 6 transitions, 68% closed; demo_b3_0: 14 transitions per arm, 60.4% closed; demo_b3_1: 24 transitions per arm, 65.5% closed, both arms in agreement on every step; demo_b3_2: 20 transitions per arm, 51.0% closed, both arms in agreement on every step). The mapping is the starter repository's own convention (galbot.py: gripper joint open/close positions 0.0 / 1.703; action < 0 closes, >= 0 opens), but the official evaluation service has never published its expected gripper action scale, so this remains a documented convention, not a validated organizer claim.

  • Fixed-layout assumption, weakened but not removed. Multi-demo

selection picks the closest recorded start layout instead of assuming one fixed demonstration, but replay still assumes the evaluation scene starts near a recorded layout — the same premise the starter repository's own replay tooling uses.

  • CPU-side development only. All verification above ran without a

simulator. Organizer-side evaluation is the intended validation step; the team welcomes the evaluation feedback the organizers send within 5 working days and will iterate on it.

  • Resubmission. The organizers allow up to five submissions in

total including resubmissions, before the policy submission deadline of 2026-12-30 12:00 SGT, and email evaluation results within five working days of each submission. The team will resubmit an improved package if evaluation feedback calls for it.
