1. What the policy does

Multi-demonstration trajectory following for the Galbot-Mobile dual-arm chamber task in the official simulation (scene04_1.usd).

  • At reset, the policy picks the recorded demonstration whose first-frame

end-effector positions are nearest to the robot's observed initial positions. Selection happens only at reset, so a rollout never jumps between demonstrations mid-episode. Without an observation at reset the first demonstration is used.

  • During the episode it tracks a phase index into the chosen demonstration

and advances it monotonically. When the caller supplies the robot's current end-effector positions it re-anchors the phase to the demonstration point nearest the current pose within a forward window (closed-loop phase tracking); otherwise it advances one demonstration step per policy step.

  • It commands the demonstration pose at phase + lookahead for both

arms, as absolute differential-IK pose commands (use_relative_mode=False, the starter repository's own convention).

  • Both grippers are held at a fixed configurable command and wheel

velocity is commanded zero — see the honest limitation in §5.

The bundled set holds four real Batch 1 episodes (demo_0, demo_2, demo_7, demo_9), extracted from four independent recordings of the official dataset rocochallenge2025/ecm2027_sim_data (175 MB, 104,344 rows). Episode lengths: 7,471 / 5,632 / 7,566 / 5,122 steps.

2. Interfaces

Two adapters share the same core (ecm_policy/core.py, pure NumPy; multi-demo selection in ecm_policy/multidemo.py):

1. Docker policy service (ecm_policy/service.py) — the planned official submission shape, implementing the starter README's service operations health(), reset(task_info), predict(observation), close(). Defaults to multi-demo mode over data/; --trajectory <single .npz> selects the old single-demo mode. 2. In-process adapter (ecm_policy/adapter.py) — builds a MultiDemoCore when trajectory_dir / demo_dir / ECM_TRAJECTORY_DIR is set or when trajectory_path points at a directory, for use with the starter repository's own evaluation harness.

A Dockerfile is included in the repository. The starter README still lists the official Docker service transport and message schemas as pending; the service follows the operation names the starter README publishes.

Demonstration data is bundled under data/ (demo_*_ee_poses.npz, end-effector poses, shape (T, 2, 7) = [x, y, z, qw, qx, qy, qz] per arm). The extraction tool is under tools/; Batch 2 data (released 2026-11-13) can extend the set with the same tool.

5. Honest limitations

  • No gripper data. The released demonstration trajectories carry no

gripper channel, verified across all four independent Batch 1 recordings (each file contains exactly one data/demo_*/ee_poses dataset and nothing else). The policy therefore never changes gripper state. Grasp-dependent milestones cannot be earned until a gripper strategy exists. This is the single biggest known gap.

  • Fixed-layout assumption, weakened but not removed. Multi-demo

selection picks the closest recorded start layout instead of assuming one fixed demonstration, but replay still assumes the evaluation scene starts near a recorded layout — the same premise the starter repository's own replay tooling uses.

  • CPU-side development only. All verification above ran without a

simulator. Organizer-side evaluation is the intended validation step; the team welcomes the evaluation feedback the organizers send within 5 working days and will iterate on it.

  • Resubmission. The team understands resubmission is allowed before

the policy submission deadline of 2026-12-30 12:00 SGT and will resubmit an improved package (for example with Batch 2 demonstrations) if evaluation feedback calls for it.
